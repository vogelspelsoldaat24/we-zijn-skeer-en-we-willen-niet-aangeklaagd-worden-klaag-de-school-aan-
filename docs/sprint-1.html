Jullie missie

Een speelbare battle waarin de speler kan aanvallen, de tegenstander terugslaat en er een winnaar verschijnt.

User story
Als speler wil ik een monster kunnen kiezen en tegen een ander monster vechten, zodat ik het gevecht echt kan spelen.

PROCEDUREEL PHP — GEEN OOP

Nieuwe programmeerconcepten

  • Variabelen, arrays en if/else
  • Functies, parameters en return
  • Formulieracties verwerken via POST
  • PHP-sessie voor spelstatus
  • Eenvoudige beurtlogica en een winnaar bepalen

Programmeertaken

  1. Maak de aanvalsknop werkend: lees de actie uit het formulier.
  2. Bereken schade en verlaag de HP van een monster. HP wordt nooit negatief.
  3. Voeg een tegenaanval toe zolang de tegenstander leeft.
  4. Laat zien wat er gebeurde in de battle-log en wie gewonnen heeft.
  5. Bewaar HP en beurtstatus tussen klikken met de bestaande sessie.
  6. Voeg een eenvoudige reset toe. Als tijd over is: laat de speler tussen twee monsters kiezen.

Acceptatiecriteria en beoordeling: Wat is de verwachting?

  • Elke teamgenoot heeft minimaal een pullrequest voltooid.
  • Begrip van code tijdens sprint review is belangrijker dan resultaat.
  • De game is in de browser te spelen.
  • Een klik op Aanvallen leidt tot schade en een actuele HP-balk.
  • De tegenstander kan terugvechten en er is een winnaar of verliezer.
  • HP komt nooit onder nul; na winst/verlies kan de speler herstarten.
  • De spelstatus blijft behouden tussen formulieracties.
  • De game gebruikt uitsluitend procedurele PHP: arrays en functies, geen classes of objects.

Lesmomenten en Scrum-activiteiten

Lesmoment 1

18 november — Sprint Planning

  1. Korte uitleg: wat is Scrum en hoe werkt het GitHub-bord?
  2. Docent is de product owner en klant, bepaal samen wie scrum master is en wie teamlid. Scrummaster is ook samen met docent een beetje product owner. Laat de rol per sprint rouleren zodat iedereen ervaring opdoet met alle rollen.
  3. Maak met elkaar en met behulp van AI een plan voor de eerste sprint
  4. Maak het GitHub Project-bord en schrijf de eerste Issues op basis van het plan.
  5. Verdeel en assign de taken in github en maak per taak een branch waar je op kan werken.
  6. Werk aan je eigen taken / stories en maak Pull Requests review dan elkaars werk.
Lesmoment 2

25 november — Review + tussenpresentatie aan de klas

  1. Werk verder aan je eigen taken zorg dat alles werkt en klaar is voor de presentatie.
  2. Laat een live battle zien. Niet alleen screenshots.
  3. Leg één paar lastige functies uit en wijs de bijbehorende Issue/PR aan. Vertel wat jullie hebben geleerd deze sprint.
  4. Verzamel feedback van de klas en leg nieuwe ideeën vast als Issues/ taken voor de volgende sprint.
  5. Zorg dat iedereen wat verteld en zorg dat jullie voorbereid zijn voor vragen.

GitHub: wat moet zichtbaar zijn?

  • Maak Issues voor de taken en gebruik label sprint-1.
  • Zet taken op het GitHub Project-bord: Backlog → Ready → In Progress → Testing → Review → Done.
  • Werk op herkenbare branches, commit regelmatig, maak Pull Requests en vraag een review.
  • Koppel een Pull Request aan de Issue (bijvoorbeeld Closes #12).
  • Houd het bord bij en toon tijdens de presentatie jullie afgeronde Issues.

Definition of Done

  • Werkende code staat op main.
  • Acceptatiecriteria zijn getest.
  • Een teamgenoot heeft de Pull Request nagekeken.
  • Relevante Issues zijn bijgewerkt en op Done gezet.
  • De functionaliteit wordt begrepen en kan live worden gedemonstreerd en uitgelegd.
